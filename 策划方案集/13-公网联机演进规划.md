# 13 · 公网联机演进规划

> 项目:疯抢星期五 | 文档集v1.1 | 起草于 v0.14 | 2026-08-07 | 状态:规划中(尚未开工)

---

## 一、目标与非目标

**目标**:从当前的局域网联机(v0.13/v0.14)演进到**公域网多人在线**,支持
陌生人匹配、跨网络对局、可信的局外经济与个人升级。

**非目标(明确不做)**:

| 不做 | 理由 |
|------|------|
| 确定性 lockstep | 物理是Jolt 刚体(购物车/商品堆叠),跨平台浮点不保证一致,做不到 |
| 完整回滚重放(rollback) | 需要确定性物理 + 状态快照回卷,对刚体堆叠场景成本极高、收益低 |
| 大规模同服(MMO) | 本作是5 分钟小局6 人对抗,不需要 |
| 自研中继/穿透| 优先用成熟方案,自研只在成本明确划算时考虑 |

**同步模型的选定路线**:**服务器权威 + 状态同步 + 局部客户端预测**。
只预测"自己角色的徒步/推车位移",碰撞结果与他人/物品一律等服务器裁决。
这是物理闹剧类游戏的务实做法。

## 二、现状盘点:哪些能直接用,哪些是局域网假设

当前实现已经具备几项**关键的公网友好特性**(是意外的架构红利,要保住):

| 已具备 | 说明 |
|--------|------|
| ✅ 服务器权威 | 物理/AI/计时/计分全在主机算,客户端只发输入(`net.gd`)。这是公网的正确起点 |
| ✅ 世界零传输 | 开局只下发种子,各端跑同一段生成代码(`market_builder` + `map_layout`) |
| ✅ 逻辑可无渲染运行 | `--headless` 能跑完整对局(`tools/smoke_test.ps1`),**等于专用服务器已经半成品** |
| ✅ 输入与模拟已分离 | 远程玩家走 `set_net_input()`,不读本机 `Input`(`player.gd`) |
| ✅ 协议版本校验 | `NET_VERSION` 握手拒绝不一致 |
| ✅ 拆包控MTU | 玩家/车辆/世界三包分离,已考虑包体上限 |

以下是**必须改造的局域网假设**,按改造成本排序:

| # | 局域网假设 | 位置 | 公网影响 |
|---|-----------|------|---------|
| 1 | 直接 new `ENetMultiplayerPeer` 并 `create_server/create_client(ip, PORT)` | `net.gd`建/连房| 公网有 NAT,绝大多数玩家无法被直连 |
| 2 | 手输 IP 建/加房| `start_menu.gd` | 无匹配、无房间列表、无邀请码 |
| 3 | 无客户端预测,纯插值渲染 | `client_view.gd` | LAN 30-80ms 可忍,公网 80-200ms 推车手感会明显发飘 |
| 4 | 状态是**全量快照**,无 delta、无兴趣管理 | `net.gd::_gather_*` | 带宽随人数线性涨;抖动/丢包下画面跳 |
| 5 | 用 Variant(Array/Dictionary)序列化 | 所有 `sync_state` | 体积远大于紧凑二进制,浪费公网带宽 |
| 6 | 时间按 `delta` 累加,非固定 tick | `main.gd` 计时/技能CD | 预测、纠正、回放、服务端仲裁都需要 tick 对齐 |
| 7 | 主机是玩家 | 架构 | 主机零延迟且掌握权威,公网竞技不公平且主机可作弊 |
| 8 | 无断线重连 | `net.gd::_on_peer_left` | 公网瞬断很常见,直接退场体验极差 |
| 9 | 元进度存本地 `user://profile.cfg` | `player_profile.gd` | **资金/升级放本地=可随意篡改**,与《01·三》的养成设计直接冲突 |
| 10 | 无 RTT/丢包可观测性 | — | 公网调优没有数据无法进行 |
| 11 | `MAX_CLIENTS` 与座位数硬编码 | `net.gd` | 扩容/观战需改多处 |

> **已修复**:客户端上报的移动矢量原先未做任何校验,而推车油门
> `throttle := -input.y` 直接乘进 `apply_central_force`——改过的客户端发
> `mv=(0,-50)` 即可把推力与撞击动能放大数十倍(徒步路径有 `normalized()`
> 兜住,推车路径没有)。v0.14 已在 `client_input`/`client_action` 的权威边界
> 加入有限性检查与长度钳制。**这正是"公网必须校验一切远程输入"的活样本。**

## 三、三个必须先定的架构决策

### 决策 1:拓扑 —— 专用服务器 vs 玩家主机

| 方案 | 优点 | 缺点 |
|------|------|------|
| A.纯 P2P/玩家主机 + 中继 | 零服务器成本 | 主机优势不公平、主机可作弊、主机退出即散场 |
| B. **专用服务器(推荐)** | 公平、可信、可重连、可观战 | 有运营成本 |
| C. 混合:公网排位用B,私房/局域网用A | 兼顾成本与体验 | 两套路径都要维护 |

**建议选 C,但先把 B 跑通**。理由:`--headless` 已能跑完整对局,把主机逻辑
剥成专用服务器的增量成本比想象的低;而局域网直连作为"朋友局"入口应当永久保留
(这是本作聚会属性的一部分)。

### 决策 2:延迟处理的力度

推车是**连续输入 + 刚体动力学**,对延迟最敏感。分级方案:

1. **最低成本**:不预测,只做插值缓冲 + 输入提示。公网 <80ms 勉强可玩。
2. **推荐**:预测自己的位移(角色/车的运动学),服务器纠正时做平滑收敛;
   碰撞/失衡/拾取一律服务器裁决后播反馈。
3. **不做**:全量回滚。

第2 档的关键取舍:**预测自己推的车会与服务器结果分歧**(因为碰撞在服务器算)。
处理办法是"分歧超过阈值就硬切,否则数帧内插值收敛",并在碰撞发生的瞬间
**放弃本地预测、直接采信服务器**(碰撞是本作的高光时刻,宁可迟一点也要一致)。

### 决策 3:元进度的权威归属

《01·三》的"局外高价出手→ 资金 → 个人升级"一旦上公网,**必须服务端权威**。
否则改本地存档就能无限资金。这条决定了:

- 对局结算结果由服务器计算并入账,客户端只展示
- 商品价格表、折扣、升级树数值由服务器下发(或至少服务端校验)
- `PlayerProfile` 需要拆成"表现层偏好(昵称/配色,可本地)"与
  "经济数据(资金/升级,必须远端)"两类

## 四、分阶段路线图

### 阶段 0 · 架构准备(不引入任何网络新特性)

见第五节。**目标是把"以后必然要改的地方"提前隔离好**,可以与正常内容开发并行。

### 阶段 1 · 可连通(能跨网络打起来)

- 传输层接入中继/穿透方案(候选:Steam Datagram Relay、Godot WebRTC + 信令服、
  云主机上的自建 relay)
- 最小房间服务:创建房间→拿邀请码→用码加入
- 断线重连(保留座位与购物车 N 秒)
- 验收:两台不同网络的机器,凭邀请码完成一整局

### 阶段 2 · 可用(手感与带宽达标)

- 本地预测 + 服务器纠正(决策 2 第 2 档)
- 状态 delta 编码 + 数值量化 + 紧凑二进制序列化
- 兴趣管理:远处的商品/大妈降频或不发
- 时钟同步与插值缓冲自适应(按实测 RTT/抖动调整)
- 可观测性:RTT/丢包/包大小/纠正次数上F1 面板
- 验收:注入 120ms 延迟 + 2% 丢包,推车与撞击仍可接受

### 阶段 3 · 可信(公平与经济安全)

- 专用服务器部署(容器化,一局一实例或一进程多局)
- 账号体系 + 服务端存档(资金/升级)
- 服务端输入校验全覆盖(速度/位置/冷却/交互距离/拾取合法性)
- 反作弊基线:位置突变检测、技能CD服务端计时、结算只认服务器
- 验收:客户端篡改内存/存档无法影响结算与资金

### 阶段 4 · 可运营

- 匹配队列与分房、房间列表、观战、举报与封禁
- 版本灰度与强制更新、服务端热更配置
- 遥测与对局回放(用于客诉与平衡调优)

## 五、现在就该做的准备(阶段 0 · 低成本高杠杆)

按"现在做便宜、以后做贵"排序。这些改动**都不改变现有玩法与局域网表现**。

| 优先 | 准备项 | 具体做法 | 现在成本 |
|------|--------|---------|---------|
| P0 | **远程输入校验**(已完成) | 权威边界钳制长度、拒绝 NaN/inf | 已做 |
| P1 | **传输层抽象** | 把ENet 的 3 处调用收进 `NetTransport` 接口(`host()/join()/close()`),`net.gd` 只依赖接口。以后加 relay/WebRTC 实现即可| 低:调用点只有 3 处 |
| P2 | **固定 tick 化** | `elapsed += delta` 改为 `tick += 1` + `TICK_DT` 常量;技能CD、扫码、打烊全部按 tick 计。预测/纠正/回放/服务端仲裁的共同前提 | 中:但越晚越贵 |
| P3 | **输入帧结构化** | `client_input` 的散参数改为 `InputFrame{tick, mv, buttons(位掩码), yaw}`,带序号。丢包补偿与预测确认都依赖序号 | 低 |
| P4 | **状态快照 schema 化** | `_gather_*` 的裸 Array 改为显式 schema(字段名/顺序/量化精度写在一处),为 delta 与二进制编码留位置 | 低 |
| P5 | **元进度存储抽象** | `PlayerProfile` 拆为 `cosmetic`(本地)与 `economy`(将来远端);读写走 `ProfileStore` 接口 | 低:趁经济系统还没写 |
| P6 | **AOI钩子** | 广播由 `rpc(...)` 改为 `for peer: rpc_id(peer, gather_for(peer))`,先让`gather_for` 返回全量。以后填过滤逻辑不动调用方 | 低 |
| P7 | **可观测性面板** | F1 面板加 RTT/丢包/上下行包大小/每秒纠正次数 | 低 |
| P8 | **网络损伤测试开关** | 测试钩子注入人为延迟/丢包/乱序(`WHITEBOX_LAG=120`之类),让公网问题在局域网就能复现 | 低:且立刻能用 |
| P9 | **握手信息结构化** | 握手除 `NET_VERSION` 外带上最小兼容版本、构建号、平台,给灰度留空间 | 低 |
| P10 | **服务端形态预研** | 用现有 `--headless` 跑一个"无本地玩家"的纯服务端模式(座位 0 不生成玩家),验证逻辑能否脱离本地玩家运行 | 中:但能提前暴露耦合 |

**建议的动手顺序**:P8 → P1 → P3 → P4 → P7 → P2 → P5 → P6 → P10。
先做P8(网络损伤注入)的理由是:**它让后续每一项改动都能被立刻验证**,
否则我们对公网表现只能靠猜。

## 六、需要的服务端组件(阶段 1起)

| 组件 | 职责 | 备选方案 |
|------|------|---------|
| 信令/房间服 | 建房、邀请码、成员表、开局广播 | 自建轻量 HTTP+WS;或 Nakama |
| 中继/穿透 | 跨 NAT 连通 | Steam Datagram Relay(若上 Steam)、TURN、自建 UDP relay |
| 对局服务器 | 跑权威模拟 | 直接复用 Godot `--headless` 导出的服务端构建 |
| 账号与存档 | 身份、资金、升级树 | 平台账号(Steam)+ 自建后端 |
| 遥测 | 对局日志、崩溃、平衡数据 | 后置,阶段 4 |

> 若确定发行在 Steam,SDR + Steam 账号能一次性解决穿透与身份两大问题,
> 应作为首选评估路径。

## 七、风险登记

| 风险 | 影响 | 缓解 |
|------|------|------|
| 推车手感在公网不可接受 | 核心玩法受损 | 尽早用 P8 注入延迟实测,必要时调整推车物理参数(加大阻尼/降低最高速)以降低延迟敏感度 |
| 刚体堆叠状态同步开销大 | 带宽超标 | 商品只在状态变化时发;静置商品完全不发;远处降频 |
| 专用服务器成本 | 运营压力 | 混合拓扑:公网排位用专服,私房走 P2P |
| 物理跨版本行为漂移 | 各端表现不一致 | 服务器权威已经规避;锁定引擎版本并纳入回归|
| 经济数值一旦上线难改 | 平衡失控 | 数值服务端下发,不写死在客户端 |

## 八、验证方法

沿用 `tools/smoke_test.ps1`的思路扩展:

- **网络损伤矩阵**:{0, 60, 120, 200}ms × {0, 1%, 5%}丢包 × {有/无抖动},
  跑满员对局并断言 stderr 全空、无位置突变、结算一致
- **一致性断言**:同一 seed 下各端的货位/清单/结算必须逐字一致
- **重连用例**:对局中强杀某客户端进程后重启,应能回到原座位
- **反作弊用例**:构造超范围输入/篡改存档,断言服务器拒绝且结算不受影响
- UI 类改动仍需人工目视(无头测试的固有盲区)
